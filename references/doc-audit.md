# 文档一致性审计：文档声称 vs 中立事实源

Roundabout 的介绍类载体有 6 份（`README.md` / `API.md` / `WORKFLOWS.md` / `pyproject.toml` /
`models.yaml` 的 description / `mcp_server.py` 的工具描述），外加 `__init__.py` 与 `.env.example` 的示例。
它们**没有任何自动同步** —— 改机制时只改「说它已下线」的地方、忘了改「把它当能力讲」的地方，
就会出现「同一件事有两种说法」。

审计口诀：**不要只做文档之间的互相对齐**，先从代码与数据重建事实基线，再逐条比对每份文档的声称。

## 事实源清单（声称要从这里核，不从别的文档核）

| 事实 | 唯一可信来源 |
|---|---|
| 模型名册 / 别名 / defaults / capabilities / bindings / `vram_tiers` | `models.yaml` |
| 工作流引用的权重文件 | 遍历 `workflows/*.json` 的 JSON 树（**按值扫 `.safetensors`，别按字段名白名单** —— 曾因漏了 `bg_removal_name` / `upscaler_model` 两个字段名少数了 2 个文件） |
| 节点路径 / 参数落点 | `workflows/*.json` 的节点实参 + `models.yaml` 的 bindings |
| 分辨率档位 / 注意力档位 / 白名单 | `gateway/params.py` 的常量；白名单本体在 `gateway/registry.py` 的 `KNOWN_PARAMS` |
| 任务保留时长 / TTL | `gateway/store.py` / `gateway/tasks.py` / `gateway/config.py` |
| MCP 工具数与形参 | `mcp_server.py` 的 `@mcp.tool(name=..., description=...)` 定义块（**不是** `README` 里的清单） |
| REST 字段与枚举 | `gateway/schemas.py` |
| **某次运行实际跑了什么** | ① `/history` 的提交图 ② `logs/comfyui_*.log` 的 `N/M` 行 ③ **产物内嵌的提交图**（`.png` 的 `prompt` tag / `.mp4` 的 metadata） |
| 计数类（几支模型 / 几个工作流 / 几个权重 / 几个工具） | **一律脚本枚举**，不要靠记忆或文档里的旧数 |

## 六个高发错类

1. **计数漂移** —— 「20 个工作流」实际 16 个文件（15 支注册 + 1 示例）；「23 个权重」是**表行数**
   而非引用数（实际 20）。新增/下线一次就会漂。
2. **节点 id 过期** —— 拓扑改过（如 `156→159`、删 `157`、子图新增 `105:221`）后，文档里的
   落点示例会指向不存在的节点。
3. **名册残留** —— 下线的档还挂在模型表 / 参数提醒里；示例里用的模型名已不在册
   （曾出现 `sdxl` / `Ideogram4` 这类上游遗留示例）。
4. **把机制名字当成事实** —— 例：把 ComfyUI 的**采样节点名** `ModelSamplingAuraFlow`
   写成 Z-Image 的**模型架构**（真身是 S3-DiT 单流扩散 Transformer）。凡「XX 架构」类断言，
   回模型原厂说明核一遍。
5. **悬空引用** —— 指向别处已删的小节（`pyproject.toml` 曾引用 README「环境要求」，而那节不存在）；
   同一件事实在 README 与 `WORKFLOWS.md` 各写一份，改一份漏一份。
6. **把已移除的机制当卖点讲** —— 最隐蔽的一类：下线时只改了「说它已下线」的地方，
   **开头宣言 / 小标题里「把它当能力讲」的句子没动**。查法：`git log -S "<关键词>"` 找出引入它的提交，
   再确认下线提交是否碰过那一行。

## 一个专门的类：性能数字

**不要把实测耗时 / 加速比 / 算力预测写进文档。** GPU、驱动、并发、显存档都会让同一份工作流
差出成倍时间，写进文档只会变成需要持续维护的错数（曾出现「lift 实测约 9 分钟」与实际
（同配置 7 分半）对不上、且日志里找不到对应那次运行的记录）。

同类要删的还有：只在某一台机器某一次成立的**数据比对**（`+152%`、`0.76x` 这类）。
**判据**：这个数字换个机器/换次运行还成立吗？
- 换机器就不成立 → 删掉，只留定性描述（「更快、更省显存」「纹理强于白放大」）。
- 结构性事实（如「输出 = 画布 × scale」、通道判别的相对关系 485Hz vs -44dB 元数据）→ 可以留。
- **通道是否生效**这类判据要用相对关系表达（贴近参考 = 生效），不要写成绝对耗时。

## 审计仪式

1. 列事实基线（脚本，输出 json/txt）；
2. 扫全部文档载体的关键词（模型名、节点号、计数、参数名、时间单位），标「待查」；
3. 逐条回事实源核 —— **能用脚本比的就用脚本**（计数、节点存在性、文件引用），
   只有语义类（「这句话还算不算卖点」）才人来判；
4. 把结论落成一份审计报告（逐条给「文档声称 → 中立事实 → 判定」三列），别只在对话里说；
5. 修完把「已核实一致」的项也列出来 —— 下一个人需要知道哪些不用再查。

工具：`sed` 不可用时（本机 Bash 工具报废）一律用 Python 脚本读改；全仓关键词扫描要**显式排除**
`.git` / `.cache` / `__pycache__`，`.workbuddy/` 被 ripgrep 默认跳过、要单独放进 `os.walk`。
